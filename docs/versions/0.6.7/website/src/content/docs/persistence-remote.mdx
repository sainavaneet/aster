title: Persistence and remote access
description: Detach from Aster, reattach later, use named sessions, and connect over SSH.
---

Aster keeps panes running in a background server. Your terminal client can detach and reconnect later.

For the local, SSH, and `aster --remote` workflows, see [How to work with Aster](/docs/how-to-work/).

## Detach and reattach

Start Aster:

```bash
aster
```

Detach the client with `ctrl+b q`.

Your panes and agents keep running. Reattach by running Aster again:

```bash
aster
```

If you want to end the session and stop its panes, stop the default server:

```bash
aster server stop
```

When Aster starts again after a full server stop, it restores the saved session shape. For what survives detach, server restart, screen history replay, native agent session restore, and live handoff, see [Session state and restore](/docs/session-state/).

## Named sessions

Use named sessions when you want independent Aster servers.

```bash
aster session list
aster session attach work
aster session attach side-project
aster session stop work
aster session delete side-project
```

A named session has its own panes, tabs, workspaces, sockets, and runtime state. It still shares the same global config file.

Use `--json` for scripts:

```bash
aster session list --json
aster session stop work --json
aster session delete side-project --json
```

## Remote attach over SSH

Run Aster on a server and attach from any SSH client:

```bash
ssh you@server
aster
```

In this mode your shell is remote, Aster runs on the remote host, and panes keep running there after you detach.

You can also attach through SSH from your local machine:

```bash
aster --remote workbox
aster --remote ssh://you@server:2222
```

In this mode your local Aster is a thin client. It connects over SSH, starts or attaches to the remote Aster server, and streams the UI back to your local terminal. Because the client runs locally, Aster can bridge local desktop features such as image clipboard paste into the remote session by copying the image to a remote temp file and pasting that path.

By default, `aster --remote` uses your local Aster keybindings for that attach. This keeps local muscle memory even when the remote server has different config. The local keybindings are a snapshot from attach time; detach and reattach after editing local keybindings. Use `--remote-keybindings server` when you want the remote server config instead. Local custom command keybindings are not sent, because those commands would run on the remote host.

For repeat targets, use your SSH config:

```text
Host workbox
  HostName server.example.com
  User you
  Port 2222
```

Then attach with:

```bash
aster --remote workbox
```

Remote attach supports Linux and macOS hosts on x86_64 and aarch64. Aster checks the remote platform, prefers a matching `aster` already on the remote `PATH`, then checks `~/.local/bin/aster`. If no matching binary exists, interactive runs prompt to install one to `~/.local/bin/aster`; non-interactive runs fail instead of modifying the host. If `~/.local/bin` is not on the remote `PATH`, Aster warns after install.

By default, `aster --remote` runs the bridge through a temporary SSH config that includes your SSH config first, then adds fallback keepalive settings. Existing user keepalive settings win. Set `[remote].manage_ssh_config = false` to use plain `ssh` without Aster's generated bridge config.

By default, remote attach uses the normal restart/stop flow if it needs to replace or restart a running remote server. To opt into experimental live handoff for a supported running remote server, pass `--handoff`:

```bash
aster --remote workbox --handoff
```

If you SSH into the server first and run `aster` there, Aster runs entirely on the server. That mode is useful and simple, but it cannot access your local desktop clipboard beyond normal terminal text paste.

When your local and remote platforms match, Aster can copy the current local binary for direct installs. For Homebrew and Nix installs, or when the platforms differ, it downloads the matching release asset for the current client version from `https://raw.githubusercontent.com/sainavaneet/aster/master/distribution/latest.json`.

For local builds or custom binaries, set `ASTER_REMOTE_BINARY` to a local file path before running remote attach.

```bash
ASTER_REMOTE_BINARY=target/release/aster aster --remote workbox
```

## Remote named sessions

Use `--session` with `--remote` to attach to a named session on the remote host:

```bash
aster --remote workbox --session agents
```

## Direct terminal attach

Full Aster attach opens the whole workspace UI. Direct attach opens one server-owned terminal in your current terminal.

Attach by agent target:

```bash
aster agent attach reviewer
```

Attach by terminal ID:

```bash
aster terminal attach term_abc123
```

Direct attach streams the current rendered terminal state, then live ANSI frames. Input goes straight to that terminal.

Detach with `ctrl+b q`. Send a literal `ctrl+b` with `ctrl+b ctrl+b`.

Only one writable direct attach client owns input and resize for a terminal. Use `--takeover` to replace an existing owner:

```bash
aster terminal attach term_abc123 --takeover
```

## Single-process escape hatch

Use `--no-session` to run Aster without the background server/client split:

```bash
aster --no-session
```

This is mainly an escape hatch for debugging or compatibility. The default persistent session mode is the normal path.
